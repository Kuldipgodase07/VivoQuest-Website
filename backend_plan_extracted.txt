VivoQuest Backend Implementation Plan
Nov 15, 2026 · @Sunil
1. Purpose, scope and what the frontend implies
This plan turns the current VivoQuest web app (11 role screens, a marketplace, a payments and compliance console, and the PDF and Excel reports) into a production backend that can pass a government audit. It is written for the team that will build it: an architect, 4 to 6 backend engineers, a DBA, a DevOps engineer and QA.
The frontend today is a prototype with sample data. Reading every screen shows the backend must serve these business areas.

Design principles
Safety first for health data. Every read of a person's record is authorised, consent-checked and audit-logged.
India-resident by default. All primary data, backups and logs stay in Indian regions.
Money is a ledger. Payment state changes only through verified gateway events, and every rupee is traceable.
Modular monolith first. Clear module boundaries now, split into services only where load or team size demands it.
Nothing is deleted silently. Soft delete, retention rules and legal holds; erasure follows DPDP rules with documented exceptions.
Out of scope for this plan
The mobile app shell, clinical decision support, and live video consultation. Each can plug into the APIs defined here.
2. Target architecture and technology stack
VivoQuest runs as one modular Node.js API in front of MongoDB Atlas, all hosted on Google Cloud in the Mumbai region (asia-south1), split into eight bounded modules that can later be peeled into services without touching the data model. Every module owns its collections, identified by a name prefix.

Request path: clients reach only the edge; the edge forwards to one API; each module reads and writes only its own prefixed collections; slow work (reports, notifications, webhooks) goes through Cloud Tasks and Pub/Sub to worker services. The API and the workers are separate Cloud Run services built from one codebase, so they scale independently.
Google Cloud setup
Organisation with three projects: vq-dev, vq-stage and vq-prod, created by Terraform; folders and policies applied at the organisation level.
Region: asia-south1 (Mumbai) primary, asia-south2 (Delhi) for disaster recovery; an organisation policy restricts resource locations to these two so data cannot leave India.
Identity: each service runs as its own service account with least-privilege IAM roles; no service account keys, Workload Identity Federation for GitHub Actions.
Secrets and keys: Secret Manager for gateway keys and database URIs; Cloud KMS for CMEK and field-level encryption keys, rotated yearly.
Network: a private VPC; Cloud Run reaches MongoDB Atlas over Private Service Connect; no public database endpoint.
Cost guardrails: budgets and alerts per project at 50%, 80% and 100%; committed-use discounts only after three months of steady usage.

Rule: the browser never builds a report or an invoice itself once the backend is live. It asks the Reports service for a job and downloads the finished file from a signed URL.
4. MongoDB design
One Atlas cluster, one database per environment (vivoquest_prod, vivoquest_stage, vivoquest_dev), and 69 collections grouped by a module prefix so they sort together in Atlas.
Naming standard
Collections: lower snake_case, plural, module prefix + noun, for example care_visits. No spaces, no camelCase.
Fields: camelCase; ids are ObjectId named _id; references are named xxxId (patientId).
Every document carries createdAt, updatedAt, createdBy, schemaVersion; soft delete uses deletedAt.
Money is stored as integer paise (amountMinor) plus currency, never a float.
Dates are UTC Date values; the app renders IST.
Indexes: ix_<collection><fields>; unique ones ux<collection>_<fields>.

Migrations: versioned scripts (migrate-mongo) run in CI before a release; no manual changes in Atlas.
5. API design
A versioned REST API (OpenAPI 3.1 is the contract), JSON over HTTPS, generated client SDK for the web app.
Conventions
Base path /v1; breaking changes go to /v2 with a 12-month overlap.
Auth: Authorization Bearer JWT (15 min); refresh token rotates on every use.
Every write accepts an Idempotency-Key header; replays return the original response.
Pagination is cursor-based (limit, cursor); filters and sort are whitelisted per endpoint.
Errors follow RFC 9457 problem+json with a stable code, for example PAY_REFUND_EXCEEDS_CAPTURE.
Every response carries X-Request-Id; rate limits return 429 with Retry-After.

6. Identity, OTP login, RBAC, consent and sessions
Sign-in stays phone plus 6-digit code; the backend replaces the demo code with real SMS OTP and adds role-based and consent-based access.
send: POST /auth/otp/send creates an iam_otp_challenges row (code stored as a salted hash, 10-minute TTL, 5 attempts) and sends SMS through a DLT-registered template.
Limits: 3 sends per phone per hour, 10 per IP per hour, tracked in Redis; repeated failures lock the phone for 30 minutes.
verify: POST /auth/otp/verify returns a 15-minute access JWT and a rotating refresh token stored hashed in iam_sessions; reuse of an old refresh token revokes the whole session family.
role: the user picks Patient, Caregiver, Nurse, Clinician, Remote desk, Health plan, Marketplace seller or Administrator; privileged roles (clinician, nurse, admin) need verification by an admin before grants activate.
Admins and finance users must use MFA (TOTP) and are bound to allow-listed devices.

7. Payments: Razorpay, Stripe, settlements, refunds, invoices and GST
The backend, not the browser, creates every payment and trusts only signed provider events. Card and UPI details never touch VivoQuest servers (hosted checkout, PCI SAQ-A).
Checkout: POST /mkt/orders creates mkt_orders (status pending) and a pay_payment_intents row; the gateway order is created with an idempotency key; INR goes to Razorpay, other currencies to Stripe.
Client pays in the provider widget; the provider calls our webhook.
Webhook: verify signature, insert into pay_webhook_events (unique eventId), enqueue; the worker writes pay_transactions, marks the order paid, issues the invoice and emits notifications. Duplicate events are no-ops.
Settlement: a daily job pulls provider settlements into pay_settlements, splits fees and GST on fees, and links each pay_transactions row to its settlement.
Reconciliation: pay_reconciliations compares provider records, our transactions and the bank statement; mismatches open a ticket in cmp_approvals for finance.
Refunds: POST /pay/refunds is maker-checker; the amount can never exceed captured minus refunded; the result lands in pay_refunds and a pay_credit_notes row.
Invoices: pay_invoices numbers are gapless per financial year from sys_counters (format VQ/2026-27/000123), with GSTIN, HSN or SAC, CGST/SGST or IGST split, and an e-invoice IRN and QR where the turnover threshold applies.
Receivables: pay_receivables ages unpaid B2B and plan invoices into 0-30, 31-60, 61-90 and 90+ buckets for the finance reports.

8. Reports service

How it scales:
API is stateless; horizontal autoscaling on CPU and request rate, 3 pods minimum across 2 zones.
MongoDB: scale vertically M30 to M50 first, add read replicas for reports, then shard the three high-volume collections (care_vitals, aud_events, pay_webhook_events).
Reads that tolerate lag (reports, dashboards) use secondaries; payments and auth always read the primary.
Redis caches product catalogue, permissions and feature flags with explicit invalidation.
Queues absorb spikes; workers scale on queue depth; per-tenant rate limits protect shared capacity.
Capacity review each quarter using Atlas Performance Advisor, slow-query log (over 100 ms) and storage growth.
